六、内存限制策略分析
--------------------
项目自带 build.bash 已经实现了部分内存保护：
  - 设置 MEM_LIMIT_GB=14
  - 设置 MEM_PER_WORKER_GB=1
  - 计算 parallel_workers = min(nproc, 14/1) = 14（在当前 16 核机器上）
  - 第一阶段串行构建关键包（ros_interfaces, livox_ros_driver2, rog_map, icp_relocalization, point_lio, dbscan_cluster, communication, bt_manager, minco_planner, minco_controller），每个包 --parallel-workers 1。
  - 第二阶段并行构建剩余包，--parallel-workers 14。

问题：
  - 第二阶段 14 个包同时编译，对 16G 内存仍可能跑满。
  - 该脚本只限制“同时编译的包数”，没有显式限制每个包内部 CMake 使用的编译线程数。
  - 当单个 C++ ROS2 包（如 point_lio、rog_map）使用 PCL/Eigen 模板时，单个编译进程可能占用 1.5~2G，14 个并发进程极易超出 16G。

推荐做法：
  同时限制两个维度：
  1. --parallel-workers N : 同时编译的包数量。
  2. --cmake-args -j M   : 每个包内部 CMake 调用的最大并发编译线程数。
  这样总并发编译线程数 ≤ N × M。

七、针对 16G 内存的推荐编译命令
--------------------------------
方案 A（最保守，适合首次全量构建）：
  source /opt/ros/humble/setup.bash
  cd /home/tcr/navi_minco_bit
  colcon build \
    --symlink-install \
    --parallel-workers 1 \
    --cmake-args -j 4 -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXPORT_COMPILE_COMMANDS=1 \
    --event-handlers console_direct+ status+

  说明：一次只编译 1 个包，每个包最多 4 线程。峰值并发线程 4，内存最安全。

方案 B（兼顾速度，适合增量构建）：
  source /opt/ros/humble/setup.bash
  cd /home/tcr/navi_minco_bit
  colcon build \
    --symlink-install \
    --parallel-workers 2 \
    --cmake-args -j 4 -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXPORT_COMPILE_COMMANDS=1 \
    --event-handlers console_direct+ status+

  说明：同时编译 2 个包，每个包 4 线程，峰值并发线程 8，预计内存峰值 10~14G，留有余量。

方案 C（使用现有 build.bash，但收紧参数）：
  source /opt/ros/humble/setup.bash
  cd /home/tcr/navi_minco_bit
  MEM_LIMIT_GB=12 MEM_PER_WORKER_GB=2 bash build.bash

  说明：按现有脚本逻辑，parallel_workers = min(16, 12/2) = 6，但第二阶段仍无单包线程限制，风险高于 A/B。

八、建议执行顺序
----------------
1. 先使用方案 A 全量构建一次，确保所有包都能通过。
